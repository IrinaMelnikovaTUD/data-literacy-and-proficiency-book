1. What does “JSON” stand for?

JSON stands for JavaScript Object Notation. Even though the name references JavaScript, JSON itself is a language-independent, plain-text format.

TipSolution

JSON = JavaScript Object Notation. It is standardized in IETF RFC 8259 and ECMA-404, and can be read and written from R, Python, JavaScript, and many other languages.

Try it yourself: use jsonlite::fromJSON() to parse a tiny JSON object and see what kind of R object comes out of it.

2. Basic characteristics of JSON

Which of the following statements are correct?

  • JSON is a text syntax suitable for the interchange of semi-structured data.
  • JSON is standardized, among others, in IETF RFC 8259.
  • JSON can only be used together with the JavaScript programming language.
  • JSON has many parallels to XML.
TipSolution

The first, second and fourth statements are true. The third is false: JSON is language-independent, despite the name.

3. JSON value types

The JSON standard defines exactly five kinds of values: object, array, number, string, and the three literal names true, false, null. There is no separate “date” type — dates are simply stored as strings.

TipSolution

Object, array, number, string, and the literals true/false/null. “Date” is not a JSON value type.

4. Object syntax

An object is wrapped in curly brackets { } and holds zero or more name-value pairs, each name being a string, with a colon between name and value and a comma between pairs.

TipSolution

Curly brackets, string names, : between name and value, , between pairs — and a value can itself be another object or an array.

Try it yourself: turn a named R list into a JSON object and check that the result starts with { and ends with }.

5. Array syntax

An array is wrapped in square brackets [ ] and holds zero or more values, separated by commas — no names involved, and the values do not have to share the same type.

TipSolution

Square brackets, comma-separated values, no names, and mixed types are allowed.

6. Number syntax

A JSON number may start with a minus sign and may include an exponent (e/E). Its fractional part is separated by a dot, not a comma, and it may not have leading zeros (except the single zero right before a decimal point).

TipSolution

-4.5E-3 is valid. 4,5 (comma as decimal separator) and 007 (leading zeros) are not valid JSON numbers.

Try it yourself: use validate() to check a JSON array that contains a number with a leading zero.

7. String syntax

A JSON string always uses double quotation marks. Certain characters (like " and \) must be escaped with a backslash, and any Unicode code point can be written as a hexadecimal escape sequence such as \u0041.

TipSolution

Double quotes only; \" and \\ are escaped characters; \u0041 decodes to the letter A.

8. Find the errors

Look at this JSON text describing two bus trips:

[
  {
    "Operator": "DVB",
    "Vehicle": Stadtbus,
    "LineNr": "85",
  }
  {
    "Operator": "DVB",
    "Vehicle": "Stadtbus",
    "LineNr": 85
  }
]
TipSolution

Three real problems: Stadtbus is missing quotation marks, there is a trailing comma after "LineNr": "85", and there is no comma between the two objects inside the array. "LineNr": 85 without quotes in the second object is not an error — numbers are never quoted in JSON.

Try it yourself: confirm with validate() that the broken text is invalid, then fix it.

9. A genuine limitation of JSON

JSON has no built-in way to represent infinity or “not a number” (NaN) — unlike, say, nested/hierarchical data, which it handles just fine through objects and arrays.

TipSolution

No representation for Inf/NaN is a real limitation. Nested data, optional schemas, and human readability are not limitations of JSON.

Try it yourself: see what happens when you try to convert NaN and Inf to JSON with toJSON().

Notice that jsonlite falls back to representing NaN and Inf as the strings "NaN"/"Inf" — a workaround, since JSON itself has no native concept for them.

10. JSON vs. XML

Both formats are human-readable, hierarchical, and text-based, and are used for similar purposes. The main differences: JSON values are unnamed unless inside an object (every XML element has a name), the same data is usually smaller in JSON than in XML, and XML is designed to be extensible while JSON’s grammar is deliberately minimal.

TipSolution

True: readability/hierarchy, naming difference, XML extensibility vs. JSON simplicity. False: XML is not typically more compact than JSON for the same data.

12. JSON Schema and related formats

A JSON Schema describes the expected structure of a JSON text (required fields, types, …) and validating against it returns TRUE/FALSE. YAML is a superset of JSON (every valid JSON text is valid YAML, not the other way around), and GeoJSON is a JSON-based format for geographic features that can be read directly with sf::st_read().

TipSolution

True: schema defines structure, validation returns TRUE/FALSE, GeoJSON + sf::st_read(). False: YAML is a superset, not a subset, of JSON.

Try it yourself: parse a tiny GeoJSON snippet and see how many features it contains.
